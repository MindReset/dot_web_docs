---
title: コンテンツ工房に参加する
description: コンテンツソースを Dot コンテンツ工房に接続し、Dot デバイスで利用できるようにします。
---

Dot コンテンツ工房は、Dot デバイスにコンテンツを提供したいコンテンツプラットフォーム、ツール、データソース向けの入口です。送信後、Dot はコンテンツの種類、データ取得方法、認証方式、デバイス適性を確認し、連携方法を検討します。

送信フォームでは、コンテンツカテゴリ、提供方法、プラットフォームのユーザー規模、連絡先メールアドレスを入力します。以下の一覧は、説明欄に追加すると確認が進めやすい情報です。

## 対象となるコンテンツ

- 一定の頻度で更新され、小さな画面や電子ペーパーデバイスで見やすいコンテンツ。
- 出典、権利、表示許諾が明確なコンテンツ。
- RSS、REST API、OAuth 認証後の API、またはプラットフォームが提供するデータで同期できるコンテンツ。
- 要約、リマインダー、ステータス、ランキング、予定、保存済み項目、購読、パーソナライズ情報をユーザーに届けられるコンテンツ。

## 推奨資料

| 資料 | 要件 |
| --- | --- |
| コンテンツ名 | 対応する国や地域に応じて、中国語、日本語、英語の名称を提供してください。各言語は 8 文字または短い語句までを推奨します。推奨形式は `{プラットフォーム名} {具体的な内容}` です。 |
| コンテンツ紹介 | 対応する国や地域に応じて、中国語、日本語、英語の紹介文を提供してください。中国語と日本語は 50 文字以内、英語は 25 語以内を推奨します。 |
| コンテンツソース名 | Dot コンテンツ工房で表示する提供元名として使用します。 |
| コンテンツソースリンク | 必須です。公式サイト、プロダクトページ、またはコンテンツソースのホームページを推奨します。 |
| コンテンツ工房カードアイコン | 透明背景の PNG、100 x 100 px を推奨します。カード左上のアイコンとして使用します。 |
| コンテンツ工房カードカラー | 1 から 3 個の Hex カラーを提供してください。カード背景の上から下へのグラデーションに使用します。1 色のみの場合は単色背景になります。 |
| OAuth 表示アイコン | OAuth を使用する場合に必要です。透明背景の PNG、200 x 200 px を推奨し、黒背景と白背景の両方で判別できるようにしてください。 |
| 対応する国、地域、言語 | コンテンツを提供する国、地域、表示言語を記載してください。 |
| レイアウト案 | レイアウトの希望がある場合は、テキスト説明、ラフ画像、Canvas API のレイアウト構造、または Dot Skill の出力を提供できます。Dot 側でデザインすることもできます。 |
| タップ動作 | テキスト表示、Web ページ、Scheme URL、Universal Link から選択できます。 |
| デバイスまたは画面の制限 | 特定のデバイス、画面方向、縦横比に限られる場合は事前に記載してください。指定がない場合、Dot が適用範囲を判断します。 |
| 表示と利用の制限 | クレジット表記、キャッシュ、再配布、商用利用、地域制限がある場合は記載してください。 |

## コンテンツ提供方法

Dot コンテンツ工房では、以下の方法でコンテンツを接続できます。フォームで最も近い提供方法を選び、必要な詳細を説明欄に記載してください。

| 方法 | 推奨情報 |
| --- | --- |
| RSS | RSS URL、更新頻度、フィールド説明、必要なリクエストヘッダー。 |
| REST API | API ベース URL、認証方式、リクエストメソッド、パラメータ、レスポンス構造、エラー形式、レート制限。 |
| OAuth 認証後の API | ユーザー認証後、Dot が Access Token を使ってユーザー関連コンテンツを取得します。OAuth パラメータとコンテンツ API の情報が必要です。 |
| データ提供 | オンライン API がまだない場合は、提供可能なデータ形式、更新方法、更新頻度を記載してください。 |

RSS または REST API で取得する場合は、推奨キャッシュ時間と最小取得間隔も提供してください。Dot が鮮度とリクエスト負荷のバランスを取りやすくなります。

未加工のレスポンス例の提供を推奨します。REST API は 1 回のリクエストで得られる未加工の完全な JSON、RSS は未加工の完全な feed レスポンスを提供してください。

## OAuth 認証情報

ユーザーログインまたは認可が必要なコンテンツでは、OAuth 2.0 Authorization Code Flow を推奨します。以下の情報を準備してください。Client Secret は、連携確認後に安全な方法で共有してください。初回送信では、Client Secret を説明欄に貼り付けず、準備済みであることを記載してください。

| 資料 | 要件 |
| --- | --- |
| Client ID | OAuth アプリケーションの公開クライアント識別子。 |
| Client Secret | OAuth アプリケーションのクライアントシークレット。サーバー側での保管が必要か、ローテーションに対応しているかも記載してください。 |
| Authorization URL | ユーザー認可ページの URL と必要な query パラメータ。 |
| Token URL | Access Token と Refresh Token を交換するエンドポイント。 |
| Redirect URI ルール | Redirect URI の事前登録が必要か、登録数、ドメイン、HTTPS 要件を記載してください。 |
| Scope | 各 Scope の用途と、コンテンツ取得に必要な最小 Scope。 |
| Token 有効期限 | Access Token と Refresh Token の有効期限、更新可否。 |
| ユーザー情報 API | アカウント識別子を表示する場合は、ユーザー情報 API と返却フィールド。 |
| コンテンツ API | 認可後にコンテンツを取得する API、リクエストメソッド、パラメータ、レスポンス構造、エラー形式。 |
| レート制限 | 認可、Token 更新、コンテンツ取得 API のレート制限。 |
| OAuth 表示アイコン | 透明背景の PNG、200 x 200 px。黒背景と白背景の両方で判別できる必要があります。 |

OAuth フローで PKCE、独自署名、固定ヘッダー、IP 許可リスト、追加のセキュリティ確認が必要な場合は、あわせて記載してください。

## 送信

送信フォームを開き、コンテンツカテゴリ、提供方法、プラットフォームのユーザー規模を選択したうえで、記入済みテンプレートを説明欄に貼り付けてください。資料がまだそろっていない場合は、まず概要を送信し、後から詳細を補足できます。
