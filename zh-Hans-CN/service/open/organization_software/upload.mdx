在 Dot. 网页打开「我的组织 → Field Lab → 软件」。你需要是组织成员，并已[创建设备软件 ID](/docs/service/open/organization_software/software_ids)。要运行示例，请准备为项目所绑定设备编译的 OTA `.bin` 文件。

## 在网页上保存草稿

1. 点「上传新版本」，在软件列表中选 `Desk Clock`。
2. 选择「公测」，填写 `1.2.0-beta.1`。
3. 在 OTA 一栏选择 `desk-clock-1.2.0-beta.1.bin`。可分别填写简体中文、英文和日文的发布说明，然后点「保存草稿」。

## 文件和版本号

每个版本至少上传一种软件文件。单个文件最大为 32 MiB，发布说明可选。要让设备取得 OTA 下载信息，请上传 OTA 应用固件。

| 文件 | 格式 | 用途 |
| --- | --- | --- |
| 分离烧录包 | `.tgz`、`.tar.gz` | 将多个镜像分别烧录到指定地址。 |
| 完整烧录镜像 | `.bin` | 首次烧录或恢复设备。 |
| OTA 应用固件 | `.bin` | 更新已安装的软件。 |

版本号使用表中的 SemVer 格式，最多 31 个字符。内测的序号从 `alpha.1` 起，公测从 `beta.1` 起。每个设备软件 ID 的各渠道独立递增，上传前可[检查可用版本号](/docs/service/open/organization_software/organization_versions)。

| 渠道 | API 值 | 示例 | 发布方式 |
| --- | --- | --- | --- |
| 内测 | `ALPHA` | `1.2.0-alpha.1` | 从草稿直接发布。 |
| 公测 | `TESTING` | `1.2.0-beta.1` | 从草稿直接发布。 |
| 正式发布 | `RELEASED` | `1.2.0` | 提交 Dot. 审核，通过后发布。 |

## 用组织 API 上传

先[取得组织凭据](/docs/service/open/organization/credentials)和[设备软件 ID](/docs/service/open/organization_software/software_ids)。以下示例将小纸 Pico 的公测版保存为草稿。

### 1. 准备上传

向 `POST /api/authV2/organization/software/upload` 发送 JSON。设备由软件项目的绑定决定。表单会从所选文件取得文件名、字节数和 SHA-256。

下面的公测版请求包含一个 OTA 文件和三语发布说明。请使用实际的设备软件 ID 和文件数据。

```json
{
  "firmwareId": "000000000000000000000101",
  "version": "1.2.0-beta.1",
  "status": "TESTING",
  "artifacts": {
    "ota": {
      "name": "desk-clock-1.2.0-beta.1.bin",
      "size": 1176976,
      "sha256": "a4b13eb3a234a0446faeed2e1d07a22f52bf06b40b00e22f219e15211eed6b07"
    }
  },
  "releaseNotes": {
    "zh-Hans-CN": "提高时钟画面的刷新稳定性。",
    "en-US": "Improves the reliability of clock display refreshes.",
    "ja-JP": "時計表示の更新を安定させました。"
  }
}
```

响应中的 `uploadId` 用于确认本次上传。`uploads` 按文件类型提供签名地址和请求头，每次上传准备的有效期为 15 分钟，以 `expiresAt` 为准。

```json
{
  "uploadId": "000000000000000000000102",
  "expiresAt": "2030-01-01T00:15:00.000Z",
  "uploads": {
    "ota": {
      "url": "https://uploads.example.com/desk-clock-1.2.0-beta.1.bin?signature=example",
      "headers": {
        "x-cos-acl": "private"
      }
    }
  }
}
```

### 2. 上传文件

为 `uploads` 中的每个文件向其签名 URL 发送一次 `PUT`，并使用响应返回的请求头。

### 3. 确认上传

全部文件上传成功后，在 `expiresAt` 前提交 `uploadId`，使用准备上传时的 API 密钥或同一 OAuth 客户端签发的访问令牌。通过大小和 SHA-256 校验后，普通上传返回 `state: "draft"`。下一步使用响应里的版本 `id` 发布。确认请求超时后，可用相同的 `uploadId` 和凭据重试。

## 上传排查

| 错误 | 处理方法 |
| --- | --- |
| `400 ORGANIZATION_SOFTWARE_FILE_REQUIRED` | 新版本需提供至少一个文件。重新提交时可上传文件或保留已有文件。 |
| `400 ORGANIZATION_SOFTWARE_INVALID_VERSION` | 按所选渠道填写表中的版本格式。 |
| `400 ORGANIZATION_SOFTWARE_UPLOAD_EXPIRED` | 确认使用发起上传的同一 API 密钥或 OAuth 客户端。已超过 `expiresAt` 时重新准备上传。 |
| `400 ORGANIZATION_SOFTWARE_FILE_UNAVAILABLE` | 核对保留的文件是否存在于原版本。对新文件，检查 PUT 是否成功及字节数和 SHA-256 是否一致。 |
| `409 ORGANIZATION_SOFTWARE_VERSION_UNAVAILABLE` | [检查所选渠道的版本号](/docs/service/open/organization_software/organization_versions)，再选择可用版本。 |
| `409 ORGANIZATION_SOFTWARE_PROJECT_ARCHIVED` | 在网页中恢复软件 ID 后重试。 |

保存草稿后，前往[发布版本](/docs/service/open/organization_software/publish)。通过 API 操作时，请保留确认上传返回的版本 `id`。
